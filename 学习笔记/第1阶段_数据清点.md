# 第 1 阶段（上）：历史数据下载和清点

这一段做了三件事：把 football-data 的历史 CSV 全部下载下来，写一个能正确读这些文件的程序，再逐列清点“哪些数据从哪年开始有”。
还没有进数据库，也还没有模型。

做数据科学，大部分时间花在这一步。模型再好，喂进去的数据有错、有缺、或者偷看了未来，结果就没有意义。

## 1. 下载了什么

| 项目 | 数量 |
|---|---|
| 联赛 | 10 个：五大联赛 + 各自的次级联赛 |
| 文件 | 333 个 CSV（每个联赛每个赛季一个） |
| 比赛 | 127,014 场，最早 1993/94 赛季 |
| 大小 | 18 MB |

- 原始文件放在 `data/raw/football-data/`，只增不改。进行中的赛季（2026/27）每次下载存一份带日期的快照，旧的不覆盖。
- 每次下载记在数据库的 `fetch_log` 表里：哪个网址、什么时候、结果如何。
- 一个小插曲：网站对不存在的文件（比如意乙 1993/94）回的不是常见的 404“找不到”，而是 300。程序一开始把它当成“下载失败”，
  后来改成“网站没有这个文件”，并加了一条自动检查。

## 2. 读文件：为什么不能直接用 pandas 读

pandas 是处理表格的库，一行 `read_csv` 就能读 CSV。但这些文件有几个毛病：

| 问题 | 例子 | 处理 |
|---|---|---|
| 行尾多余的逗号 | 33 个文件里共 3873 行比表头多出几个空格子 | 多出的格子是空的就直接去掉；有值就记下来再去掉（只有意乙 2003/04 的 4 行） |
| 没有列名的列 | 表头里有几个空名字 | 去掉 |
| 重复的列名 | 德乙 2004/05 表头有 3 个 `LB` | 按位置改成 LBH、LBD、LBA（主胜、平、客胜） |
| 编码不统一 | 326 个文件是 UTF-8，7 个是西欧编码 cp1252 | 先试 UTF-8，不行再用 cp1252（否则 Köln 会变成乱码） |
| 日期写法不统一 | 2017/18 以前多是 `25/08/07`，2018/19 起都是 `25/08/2007` | 清洗时两种都认 |

用 pandas 的“跳过坏行”选项，那 3873 行比赛会被**悄悄丢掉**，不报错。所以另写了 `src/clean/football_data_reader.py`：
逐行读，多出的格子截掉，每处改动都记下来，最后汇报给人看。

教训：**读数据的程序不能悄悄丢东西。**丢了不报，后面统计出来的“主场胜率”之类就是错的，而且很难发现。

## 3. 数据字典：每一列是什么、什么时候知道

`config/football_data_columns.yaml` 登记了全部 230 个列名。每列写了：

| 字段 | 例子（PSCH） | 说明 |
|---|---|---|
| 含义 | 平博 主胜 收盘赔率 | 参照网站的列说明文件 notes.txt |
| 类别 | 收盘赔率 | 比赛信息、赛果、比赛统计、赛前赔率、收盘赔率等 |
| **时点** | **收盘** | 赛前 / 收盘 / 赛后，最重要的一个字段 |
| 数据项 | 平博 胜平负 收盘 | 改过名的列归到同一项，例如早年的 PH 和后来的 PSH |
| 用途 | 只用于本场评估 | 按需求文档第 17 节 |

**时点为什么最重要：防止“偷看未来”。**

预测一场比赛时，只能用开球前就知道的东西。

- 赛后：比分、射门、角球、红牌。这些是比赛的结果，不能拿来预测**这一场**，只能用来算球队**以前**的状态。
- 收盘：开球那一刻的赔率。我们的预测在开球前 24 小时、6 小时出，那时还不知道收盘赔率。它只用来**评估**：模型比收盘赔率准不准。
- 赛前：赛前一两天的赔率，可以当特征用。

如果不小心把收盘赔率或者本场射门数喂给模型，回测成绩会好得不正常，上线后却不灵。这叫“数据泄漏”。
时点字段让程序能自动检查：取特征时，凡是“赛后”“收盘”的列，只允许用以前比赛的值。

## 4. 覆盖表：哪些数据从哪年开始有

规则：一个赛季里至少 90% 的比赛有这项数据，才算“这个赛季有”。完整表在 `data/reports/football_data_覆盖汇总.md`（每次运行清点程序重新生成）。

五大联赛的情况（次级联赛大体相同，比赛统计从 2017/18 起才有）：

| 数据 | 从哪年有 | 说明 |
|---|---|---|
| 全场比分 | 1993/94 | |
| 半场比分 | 1995/96 前后 | |
| 射门、角球、黄红牌 | 英超 2000/01，其他 2005/06 前后 | 德甲 2002/03 断了一季 |
| 开球时间 | 2019/20 | 更早只有日期；是英国当地时间 |
| 裁判 | 英超、英冠 2000/01 起 | 德甲、意甲只有早年两季，其他没有 |
| xG | 2026/27（本赛季才开始） | 历史 xG 还要另找来源 |
| Bet365 赛前赔率 | 2002/03 | |
| 多家平均、最高 赛前（胜平负、大小球、亚盘） | 2005/06 | |
| 平博 胜平负 赛前和收盘 | 2012/13–2024/25 | 2025/26 中途停了 |
| 平博 大小球、亚盘 | 2019/20–2024/25 | |
| 多家平均、Bet365 收盘 | 2019/20 | |
| Betfair 交易所 | 2024/25 | |

英超逐季看平博胜平负：2012/13 到 2024/25 都是 100%，2025/26 只有 55%（2026 年 1 月后没有了），2026/27 是 0%。

### 这次发现的两件事

**1. 需求文档原来的估计有错，已改正（v0.21）。**

原来估计“收盘赔率 2019/20 起才有”，所以能和平博收盘对比的开发数据只有约 5 个赛季。
实际平博的收盘列 2012/13 起就有（和赛前值不一样的比赛占 93%–96%，说明确实是另一个时间点的价格），能对比的开发赛季是 12 个。
反过来，原来以为“多家平均收盘覆盖更长”，实际它 2019/20 起才有，比平博短。

**2. football-data 不再提供平博赔率了，这会影响设计。**

需求文档第 5 节的规则是“有平博就用平博，没有就用多家平均”，评估的标杆 1 也是平博收盘。
开发赛季几乎都有平博，但上线后（2026/27 起）football-data 没有平博了，原因没查到。

- 上线后要靠国内网站抓平博赔率（平博本来就是国内显示的 5 家主要公司之一），第 1b 阶段确认能不能抓到。
- 风险：回测时融合用的是平博，上线后如果换成多家平均，回测选出的“模型占多少比重”（w）可能不适用。
- 已记进需求文档第 18 节待定问题第 7 条。建议第 3 阶段选 w 时，再用“只用多家平均”选一次，比较差多少。

## 小练习

1. 打开 `config/football_data_columns.yaml`，搜 `HC:`。HC 名字里有 C，为什么时点不是“收盘”？
2. 有人想用“本场主队射门数”当特征预测本场胜负，回测准确率很高。问题在哪？
3. 英超 2005/06 的“多家平均 胜平负 收盘”是 0%。如果第 5 节的标杆 2 要用多家平均收盘，2005/06–2018/19 怎么办？
4. 为什么覆盖规则是“至少 90%”而不是“有一场就算有”？

<details>
<summary>答案</summary>

1. HC 是主队角球数（Home Corners），C 是 Corners，不是 Closing（收盘）。是赛后数据。判断收盘要看 C 是否紧跟在公司缩写后面，例如 PSCH = PS（平博）+ C（收盘）+ H（主胜）。
2. 射门数是比赛**打完**才知道的（时点是赛后）。预测时根本拿不到，回测准确率高是因为偷看了答案。只能用球队以前比赛的射门数。
3. 这些年份没有多家平均收盘，只能用多家平均的赛前赔率代替，并在成绩里单独标出来，不能和有收盘的年份混在一起比较（需求文档第 5 节已这样写）。
4. 有些赛季只有一部分比赛有某项数据，例如英超 2025/26 的平博赔率只有 55% 的比赛有。按“有一场就算有”，这一季会被当成有平博，用的时候才发现一半是空的。

</details>
